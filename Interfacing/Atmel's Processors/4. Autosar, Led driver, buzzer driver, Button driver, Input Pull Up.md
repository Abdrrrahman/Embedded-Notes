## Autosar Layers
Do you remember this code for toggling a pin? 
```c

	DIO_SetPinDir('A', 2, 1);

		_delay_ms(1000);
	}

```
That's the normal code for calling functions
But in Autosar states that functions calling must be in layers. 

### What are Autosar Layers (Layered Architecture)? 
Autosar Layers are three layers:
- Application Layer
- HAL (Hardware Abstraction Layer)
- MCAL (Micro-Controller Abstraction Layer)

Normally we module our project into include folder containing header files and source folder containing source files and main. 
The main file is the Application Layer. 
Th HAL is all the external hardware modules drivers like led module, button module, motors module, relay module, any external hardware module. 
The MCAL is all the internal hardware modules drivers like DIO, PWM, ADC, Timers and so on. 

Normally the sequence should be as follows:
- The main function (Application Layer) should be calling an external module function (HAL). 
- The External Module Function (HAL) should be calling an internal module function (MCAL). 

![Three layered software architecture diagram with Application Layer at the top, HAL in the middle, and MCAL at the bottom. Arrows show application code calling HAL functions, which then call MCAL drivers for microcontroller hardware access. The diagram is a clean technical illustration with neutral academic styling. Text labels read Application Layer, HAL, and MCAL.](/Interfacing/Attachments/autosar-layers.png)

So the code above isn't following the Layered Autosar Architecture, as the main (Application Layer) is calling the internal module directly (MCAL) with no HAL in between.

How to make the code above follow the Layered Architecture? 
We are trying above to control a Led, This led is considered an external module, so the best move here is that we make a driver for the led. 
The main calls the led driver and the led driver calls the dio driver. 
It seems redundant but be patient.

#### Why was it called Abstraction Layer? 
Abstraction means isolating like a remote control and a TV, When I press on a button on the remote I am waiting for some functionality to occurr without worrying how will it be implemented. 
We can say here that the functionality is isolated from the end user. 
The same rule applies on the Autosar Layers, 
The HAL is named as Hardware Abstraction Layer as the hardware is isolated from the end user in the main and also isolated from the MCAL, No one knows the real implementation except the HAL Developer. They only have the user interface layer (Function calls) to interact with the HAL with. 
The MCAL is named as Micro-Controller Abstraction Layer as the implementation is isolated from the end user in the main and from the HAL Developer, They only have the user interface layer (Function calls) to interact with the MCAL with. 

Imagine we are working on a big project and you used a specific types of LCDs, and you wanted to change it with another type that needs a new driver. If you didn't follow the autosar standards you will need to change the whole main, but if you are following the autosar standards you only replace the driver with the new one, you don't need to change the main file as the function prototypes are the same. 

#### Co-Operate on standards, Compete on the Implementation
This is a well known quote in Autosar architecture, as all the functions have the same prototypes (have the same name, return type, arguments), but the implementation differs across companies. 

### Callback Functions
Callback functions happen when you try to call a function from an upper layer. Like you are trying to call a function in *Application Layer* or *HAL* from a *MCAL*, or trying to call a function in *Application Layer* from a *HAL*.

When does Led 1 toggle? 
 At all numbers (Every Iteration). 

When does Led 2 toggle? 
At even numbers only (Every 2 Iterations). 

When does Led 3 toggle? 
At numbers divisible by 4 only (Every 4 iterations). 

So we simply can map this logic in a loop with a counter and some conditions on this counter. 

$Led_i$ toggles every $i$ iterations (i starts from 1).
We can check for this by modulo. 


```c
#define F_CPU 8000000UL
#include "led.h"
#include <util/delay.h>

int main(void) {
	
	for(uint8_t i=0; i<3; ++i) {
		led_Init('D', i);
		led_TurnOff('D', i);
	}
	
	uint8_t TheMostPowerfulCounterEver = 0;
	
	while(1) {
		_delay_ms(1000);
		
		// Happens Each second
		led_Toggle('D', 0);
		
		if(TheMostPowerfulCounterEver % 2 == 0) {
			// Happens Each 2 Seconds
			led_Toggle('D', 1);
		}
		
		if(TheMostPowerfulCounterEver % 3 == 0) {
				// Happens Each 3 Seconds
			led_Toggle('D', 2);
		}
		
		TheMostPowerfulCounterEver++;
	}
}
```

# Button Driver
Buttons has many types (DIP, Push Button, .. )

The Push button has 2 pins that are isolated (open circuit) as long as we are not pressing the button, when we press it, a short happens between the two pins closing the circuit. 

The switch button (spst) does the same but we don't need to keep pressing, we only press the switch once and it keeps conducting till we press it again. 

The DIP can be pushed and pulled, it is often packaged in many switches together. When it is pushed to ON side it closes the circuut, and when it is pulled to OFF side it opens the circuit. 

### Button Connection
If we tried to connect a button (any type of the above) to a MCU pin, The button should be an input component, I can connect it to PA2 and connect it into a 5V rail. 

In this connection, when we press the button we send a Logic High to the Pin, but when we don't press what happens?
This is known as the floating pin famous problem. 

MCUs and Normally Most of the Embedded Hardware Boards are made of TTL (Transistor-Transistor Logic) which means you are either getting your input from a transistor or you are giving your output to a transistor, or you yourself are a transistor. 

Transistors have only 2 modes: - Hungry or Horny (Kidding) - Logic Low or Logic High. 
They have nothing in between, they have no state to represent neither of them (floating) (HI-Z).

Acceptable TTL Gate Level:
- $[0V \space , \space 0.8V]$ considered Logic Low. 
- $[2V \space , \space 5V]$ considered Logic High. 

The gap between $0.8V$ and $2V$ is floating, we have no state for it, so it keeps flipping unexpectedly. 


This problem relates to our connection, when we don't press the button it is not pulled into $0V$. It's left noisy, due to electromagnetics around it keeps floating with no clue with its real logic level. So we need to pull it to $0V$ when we are not pressing the button, and pull it to $5V$ when we are pressing the button. 

This can be solved using the Pull Down Resistor.

# Internal Pull Up
The two button connections we discussed earlier was an external pull connections. 
By default we have internal pull up. To be able to understand it, we need to recap the MOSFETs. 

## MOSFETs Quick Recap

MOSFETs had two types, PMOS, and NMOS. 

MOSFETs also has 3 pins like the BJTs, One pin is called Gate, the other is called Drain and the last is called Source. 

NMOS looks like the normal diagram:

![MOSFET schematic symbol for an n channel transistor with the gate on the left and the drain and source connected through a vertical channel. The symbol is a standard circuit diagram element used in embedded hardware explanations.](/Interfacing/Attachments/Normal-Mosfet-Schematic-Symbol.png)

While the PMOS is the inversion of it donating this by a bulb inverter symbol at the Gate Pin:

![P channel MOSFET schematic symbol with an inverted gate marker, shown as a small bubble on the gate terminal. The symbol indicates that the transistor is controlled by a low logic level and is used in pull up circuits.](/Interfacing/Attachments/Inverted-Gate-Mosfet-Schematic-Symbol.png) 

In PMOS if you apply logical high to the gate the Transistor will be in *cutoff* mode (Open Circuit), if you apply logical low to it, the transistor will be in *saturation* mode (Closed Circuit). 

While in NMOS it is the opposite, when you apply logical low to the gate the transistor will be in *cutoff* mode (Open Circuit), if you apply logical High to it, the transistor will be in *saturation* mode (Closed Circuit). 

## Internal Pull Up Circuit
Normally we have inside the ATmega32 Micro-Controller an internal pull-up resistor.
This pull-up resistor is deactivated by default till you activate it manually. 

#### How is it deactivated? 
Let's take PA0 as an example, the 0 bit in the PINA register is connected to the pin of PA0 and connected also into a Pull up resistor  circuit, but this circuit is interrupted in the middle with a PMOS connected to an inverter connected to a 3 input AND gate. (3-Input NAND)

![Circuit illustration of an ATmega32 input pin with an internal pull up resistor controlled by a PMOS switch. The diagram shows a NAND gate and inverter shaping the logic that enables or disables the pull up path for the pin.](/Interfacing/Attachments/Internal-Pull-Up-Illustration.png) 

Normally, if the internal pull up is deactivated, the NAND's output should be 1 which is an input for the PMOS, which makes the PMOS operates on *cutoff* mode resulting in an open circuit, so the internal pull up circuit as a whole is ignored.

But if you activate the internal pull up, you will find the NAND's output is 0 resulting in *saturation* mode which makes the circuit closed so it operates. 

#### How to Activate the PMOS?
To activate the PMOS, you need its input to be logical low, so the output of the NAND must be logical low, to make the NAND's ouput logical low (Activate it), we need its three inputs to be logical high.

Imagine we are now talking about PA0 pin. 
Its three inputs are:
- Bit 0 of DDRA Inverted (by default is logical high - input mode - )
- Bit 2 of SFIOR Inverted (by default is logical high - enabled - )
- Bit 0 of PORTA (by default is logical low - outputing logical high - )

![Detailed datasheet schematic of the internal pull up circuit for one AVR pin. The drawing shows the DDR signal, the SFIOR PUD control signal, the PORT register signal, and a PMOS transistor switching a pull up resistor connected to the pin.](/Interfacing/Attachments/Datasheet-Input-Pull-up-Connection.png) 

##### Bit i of DDRx inverted
If the bit 0 in PINA register is logical low (input), the inversion of it is logical High, which is the first condition achieved. 
If it was an output pin (logical high), I don't need to make it an input pull up. As it is an output pin, so the inversion of it is logical low which deactivates the NAND. 

![Simplified schematic showing the inverted DDRx bit for one input pin feeding the pull up control network. The circuit indicates that the pull up can only be enabled when the pin is configured as an input.](/Interfacing/Attachments/Input-pull-up-connection-with-only-bit-i-of-DDRx-inverted.png)

##### Bit 2 of SFIOR Inverted
This is one of the special function registers (I/O Registers), Its name is Special Function Input Output Register. 

![Excerpt from the AVR SFIOR datasheet showing the PUD bit in the special function register. The highlighted control bit disables all internal pull up resistors when set to a logic high state.](/Interfacing/Attachments/SFIOR-Datasheet.png) 

The third bit in this register - Bit 2 - is named as - Pull Up Disable - PUD bit.
This bit is responsible for disabling the Input pull-up, It is connected through inversion to all the input pull up circuits of all bits. 

Its default state logical low which is inverted into logical high (Attempting to activate NAND (NAND outputing logical low)), if you set it to logical high, it will be inverted into logical low (Attemptibg to deactivate NAND (NAND outputing logical high)) which means disabling input pull up. 

![Simplified circuit showing the inverted DDRx control signal and the inverted SFIOR PUD signal combining to enable or disable pull up logic for one port pin. The diagram highlights that the pull up is only active when both conditions are satisfied.](/Interfacing/Attachments/Input%20pull-up-connection-with-bit-i-of-DDRx-inverted+SFIOR-bit-2-inverted.png)

> You can use this to disable all the input pull up to all pins on all ports at once, unlike other options needs to be done across each pin. 

##### Bit i of PORTx
This one is the true reason why the input pull up isn't activated by default, normally it is set to 0 (which means the PA0 outputs 0, but it is not an output, so it has no meaning). 
Normally to activate NAND, we need to set this bin to logical high (Outputing 1 even though it is an input pin). 

![Expanded pull up control schematic showing the DDRx inverted signal, the SFIOR PUD inverted signal, and the PORTx bit combining in a NAND gate. The circuit demonstrates that setting the PORT bit high enables the internal pull up resistor for the selected input pin.](/Interfacing/Attachments/Input-pull-up-connection-with-bit-i-of-DDRx-inverted+SFIOR-bit-2-inverted+bit-i-of-PORTx.png) 

Its schematic:

![Complete internal pull up circuit for one AVR port pin, showing the tri state input buffer, the PMOS switch, the resistor, and the logic inputs from DDRx, SFIOR, and PORTx. The diagram illustrates how the pull up is enabled and disabled in practice.](/Interfacing/Attachments/Datasheet-Input-Pull-up-Connection.png) 

This huge circuit is implemented for each pin in each port, We have talked earlier in the first two sessions about the Tri-state buffer part. 
You can see this time that we added to it the input pull up circuitry. 
###### Edge Case
If you have connected an output device like a led on the PA0, while you are connecting it as an internal internal pull up circuit, in simulation you won't see a difference, as the tri-state buffer disconnected the PORTA Register from the PA0, but in real life you will notice that the led will emit very very weak light, as the pull up is $5V$ connected via a PMOS on *saturation* (short circuit) connected to a $10k \Omega$ resistor that makes the current flowing into the circuit around $5mA$,  which isn't sufficient for lighting a full led, but just makes it lightened very weakly.  

## Input Pull Up Code

Normally we use this in the main to enable input pull-up on a specific pin:
```c
#include "DIO.h"

int main(void) {

	// Setting PA0 as Input Pin.
	DIO_SetPinDir('A', 0, 0);

	/*
		Setting Output Voltage to High
		This enables the NAND saturating the PMOS
		Enabling the Internal Pull-Up.
	*/
	DIO_WritePin('A', 0, 1);

	while(1) {
		/*
			Doing nothing is an Art.
		*/
	}
}
```
As a programmer, I won't realize that this is an Input Pull-Up enable code easily, so for readability we use a special function called `DIO_ConnectPullUp()`.

```c
#include "DIO.h"

int main(void) {

	DIO_SetPinDir('A', 0, 0);
	DIO_ConnectPullUp('A', 0, 1);

	while(1) {
		/*
			Doing nothing is an Art.
		*/
	}
}
```

> We are violating the AUTOSAR Architecture by making the main (Application Layer) call a function in MCAL.
But we are doing this only for simplicity for now.

```c
void DIO_ConnectPullUp(uint8_t port, uint8_t pinNum, uint8_t isPullUp) {
	/* 
		if isPullUp == 1:

		else:
			it will disable it
	*/

}
```

or you can use the MCAL way:
```c
void DIO_ConnectPullUp(uint8_t port, uint8_t pinNum, uint8_t isPullUp) {

	switch(port) {
		case 'A':

			} else {

		case 'B':
		case 'b':

				SET_BIT(PORTB, pinNum);
			} else {
				CLR_BIT(PORTB, pinNum);
			}
		break;

		case 'C':
		case 'c':
			if(isPullUp) {
				SET_BIT(PORTC, pinNum);
			} else {
				CLR_BIT(PORTC, pinNum);
			}
		break;

		case 'D':
		case 'd':
			if(isPullUp) {
				SET_BIT(PORTD, pinNum);
			} else {
				CLR_BIT(PORTD, pinNum);
			}
		break;

		default:
			/*
				Doing Nothing is an Art.
			*/
		break;
	}
}
```

Imagine we have connected a pull up resistor button to PA2, and connected also a led to PA7.

We want the code to toggle the led every time we press the button.

```c
#include "Led.h"
#include "DIO.h"
#include "Button.h"

int main(void) {

	Button_Init('A', 2);
	Led_Init('A', 7);

	while(1) {
		if(Button_ReadState('A', 2)) {
			Led_Toggle('A', 7);
		}
	}
}
```

This code seems fine, but it has a problem. A normal person when pressing a button, he keeps pressing (holding the button) for about $15 ms$ which is much lower than the speed of the processor, if we imagine that its speed is $1ms$, This means that the processor keeps reading the state 15 times which will make it toggle for 15 times.

That is not what we want.
We want that once we press the button it toggles once even if we hold the pressing for 5 seconds, it must be considered as only 1 press.

The solution for this is not in the connection, it is in the code.

A solution is to add `_delay_ms(200)` in each iteration so the processor doesn't read until you remove your finger from pressing.

```c
#define F_CPU 8000000UL
#include "Led.h"
#include "DIO.h"
#include "Button.h"
#include <util/delay.h>

int main(void) {

	Button_Init('A', 2);
	Led_Init('A', 7);

	while(1) {
		if(Button_ReadState('A', 2)) {
			Led_Toggle('A', 7);
		}

		_delay_ms(200);
	}
}
```

But this solution is not the best solution, as if we kept pressing for 5 seconds, this solution fails.

We will discuss the better solution after talking about "Mechanical Switches" more.

# Mechanical Switch VS Electrical Switch
Unlike Transistors which are considered an 'Electrical Switch', the switch that we press by our fingers is called a 'Mechanical Switch'.

The Electrical Switches are much faster than the mechanical ones as they are switching depending on electrical pulses where each transistor has a maximum switching frequency. 

The Mechanical Switches has an associated problem with them that only appears on physical devices not the simulated ones.
This problem is the *Switch Bouncing*. 

Bouncing means oscillating, like a ball that bounces on a floor till it rests (Dumped Oscillation).

We talked earlier in this article that when we press on a button we are making a short circuit between the two terminals (Delivering High Voltage in Pull Down Resistor Connection) and we don't press it we are making an open circuit between the two terminals (Delivering Low Voltage in Pull Down Resistor Connection).

![Pull-down resistor pushbutton circuit schematic. The circuit shows a voltage source connected through a pushbutton switch to ground, with a pull-down resistor connecting the input signal line to ground. When the button is pressed, the input line goes high. When released, the pull-down resistor brings the input line back to ground, producing a low logic level. Technical schematic with clean lines on light background, neutral presentation.](/Interfacing/Attachments/Button-No-Bouncing.png)

The actual truth that this doesn't happen, it bounces every time the state changes, it oscillates till it rests on the true state of the button. 

> This happens as the plates of the switch contacts each other dozens of times in milliseconds.

This bouncing in almost cases it is between $20-30 ms$.

This problem happens in relays and push buttons.

![Switch bouncing behavior diagram showing oscilloscope waveform and circuit schematic. The waveform displays voltage oscillations immediately after button press, with the signal bouncing up and down rapidly multiple times before settling to a steady high level. The circuit schematic shows switch contacts that make and break repeatedly during bouncing. The visualization demonstrates the mechanical nature of contact bouncing and the time period before the signal stabilizes. Technical diagram with neutral styling, no text elements.](/Interfacing/Attachments/Button-Bouncing.png)

Solutions for this problem are called 'Switch Debouncing'. We have many approaches to solve it.

## Software Debouncing
We already know that this bouncing takes around $20-30 ms$, we can check 2 times and add a delay time between them.

This code turns on a led when we press on a button.
```c
#define F_CPU 8000000UL
#include "Led.h"
#include "DIO.h"
#include "Button.h"
#include <util/delay.h>

int main(void) {

	Button_Init('A', 2);
	Led_Init('A', 7);

	while(1) {
		if(Button_ReadState('A', 2)) {
			
			/* 
				Waiting to make sure the bouncing is dumped.
			*/
			_delay_ms(40);
			
			/* 
				Check again.
			*/
			if(Button_ReadState('A', 2)) {
				Led_TurnOn('A', 7);
			}
		}
	}
}
```

Software Debouncing - This approach - is not the best approach, as it doesn't solve the problem itself, it only ignores it and it adds unnecessary delay to the system.
This simple solution is used with a system that has no *interrupts* or *RTOS*.

### Why is this solution working?
If you check on the button's state while it's bouncing you can read logical low (bouncing) while you are litterly still pressing.

# Back to Toggle
Now let's return to our problem, we know now that we have an initial problem called *Switch Bouncing*, that is solved using different ways either software or hardware, and there is another problem that is still unsolved called *Switch Contact* that we face when we keep pressing on a button.

To solve the *Switch Contact* problem we can try our first approach using a flag.

## Flag Approach

> Assuming we apply *Hardware Debouncing* and we use an input pull down resistor button conneciton.

```c
#define F_CPU 8000000UL
#include "Led.h"
#include "DIO.h"
#include "Button.h"
#include <util/delay.h>

// This is the flag.
uint8_t firstPressed = 1;

int main(void) {

	Button_Init('A', 2);
	Led_Init('A', 7);

	while(1) {
		if(Button_ReadState('A', 2) && firstPressed) {
			// This is the first iteration in the press

			Led_Toggle('A', 7);

			// You set it to false to prevent other iteration in the same instant from getting inside the condition.
			firstPressed = 0;
		} else if(!Button_ReadState('A', 2)){
			// Button is released

			firstPressed = 1;
			// Flag is set to true again for next time you press.
		}

		// Other iteration while the button is pressed in the same instants executes here (Doing Nothing is an Art.)

		_delay_ms(10);
		// This delay is to give MCU some breath.
	}
}
```

This flag is used only to indicate if this flag is pressed for the first time in this press.
The condition checks if it reads logical high this means that the button is pressed, this is not enough: As we may be pressing the button for the first time in the same press, or it may be a second press in the same press.
To identify in which iteration are we in the same press we can use th flag.
Initially the flag `firstPressed` is set to `true` which means once you hit the button, this will be the first press, you now must set this flag to `false` to prevent it from toggling again in the next iteration.

When do I release the flag to true again?

This happens when you release the button aka `! Button_ReadState()`.

Summary:
- I am looping doing nothing from second iteration with button pressed till I release the button.
- I detect releaseing and pressing the button using `Button_ReadState()`.
- I detect pressing the button for the first time or other times using `firstPressed`.

> If We assume no *Hardware Bouncing* we need to apply *Software Bouncing* and we use an input pull down resistor button conneciton.

```c
#define F_CPU 8000000UL
#include "Led.h"
#include "DIO.h"
#include "Button.h"
#include <util/delay.h>

// This is the flag.
uint8_t firstPressed = 1;

int main(void) {

	Button_Init('A', 2);
	Led_Init('A', 7);

	while(1) {

		if(Button_ReadState('A', 2)) {

			/* 
				Waiting to make sure the bouncing is dumped.
			*/
			_delay_ms(40);
			

			/* 
				Check again.
			*/
			if(Button_ReadState('A', 2) && firstPressed) {
				Led_Toggle('A', 7);
				firstPressed = 0;
			} else if(!Button_ReadState('A', 2)){
				firstPressed = 1;
			}

		}

		_delay_ms(10);
		// This delay is to give MCU some breath.
	}
}
```

> You can change the name of the flag to something like `isPressed` or `prevVal` but you will need to invert its logic for a better readablity.

Another Solution is to try Loop Approach.

## Loop Approach
If you noticed, the Flag approach is a little bit complicated to understand, the Loop approach is much easier although they are doing the same thing, looping doing nothing till we remove our finger, till we release the button.

> Assuming we apply *Hardware Debouncing* and we use an input pull down resistor button conneciton.

```c
#define F_CPU 8000000UL
#include "Led.h"
#include "DIO.h"
#include "Button.h"
#include <util/delay.h>

int main(void) {

	Button_Init('A', 2);
	Led_Init('A', 7);

	while(1) {

		if(Button_ReadState('A', 2)) {
			Led_Toggle('A', 7);

			while(Button_ReadState('A', 2));
			// Looping doing nothing till the button is released.
		}

		_delay_ms(10);
		// This delay is to give MCU some breath.
	}
}
```
