## Compiling and Uploading

This can be done through two approaches:

First one is to manually set everything during compiling in the terminal

Second one is to set everything once at a Makefile that we use to compile.

### Terminal Commands

If you don't use the Makefile, you must run the three core toolchain commands manually in your terminal every time you want to build and flash your code.

```bash
avr-gcc -Os -Wall -mmcu=atmega32 -DF_CPU=16000000UL main.c -o main.elf
avr-objcopy -O ihex -R .eeprom main.elf main.hex
avrdude -c usbasp -p m32 -U flash:w:main.hex:i
```
#### First Command

```bash
avr-gcc -Os -Wall -mmcu=atmega32 -DF_CPU=16000000UL main.c -o main.elf
```

This command takes your main.c source code, applies the optimization (`-Os`) and warning (`-Wall`) flags for the ATmega32 at 16 MHz, and outputs an ELF (Executable and Linkable Format) file containing your compiled program.

> You have to set the `-mmcu`, `-DF_CPU` and `-Os` to the correct configurations you use.

#### Second Command

```bash
avr-objcopy -O ihex -R .eeprom main.elf main.hex
```

The microcontroller cannot read an ELF file directly. This utility extracts the raw machine instructions from the ELF file and formats them into a plain-text Intel HEX file (main.hex), ignoring any EEPROM data sections (-R .eeprom).

#### Third Command

```bash
avrdude -c usbasp -p m32 -U flash:w:main.hex:i
```

This tool connects to the usbasp programmer, targets the ATmega32 (m32), and writes the .hex file directly into the microcontroller's flash memory.

> You have to se the `m32` to the correct configurations you use.

If your project grows and you have multiple C files (e.g., `main.c`, `uart.c`, `timer.c`), you simply list all of them in the first command before the `-o` output flag:

```bash
avr-gcc -Os -Wall -mmcu=atmega32 -DF_CPU=16000000UL main.c uart.c timer.c -o main.elf
```

### AUTOSAR Compilation

Normally you will follow AUTOSAR Layered Architecture, so you will have different folders like "MCAL" and "HAL".

You must explicitly tell the compiler two things: where to find the source files (.c) and where to search for the header files (.h).

```bash
avr-gcc -Os -Wall -mmcu=atmega32 -DF_CPU=16000000UL -I./MCAL -I./HAL main.c MCAL/DIO.c HAL/LED.c -o main.elf
```

> (The `avr-objcopy` and `avrdude` commands remain exactly the same as before).

Typing the path for every single .c file manually becomes extremely tedious as your layered architecture grows. You can use terminal wildcards to grab every C file inside those directories automatically:

```bash
avr-gcc -Os -Wall -mmcu=atmega32 -DF_CPU=16000000UL -I./MCAL -I./HAL main.c MCAL/*.c HAL/*.c -o main.elf
```

#### Header Files

By default, the compiler only looks for headers in the standard system libraries and the exact folder where the current `.c` file lives. To let it find your custom headers globally (so `#include "DIO.h"` works perfectly from any file), you must add the -I flag followed by the folder path for every directory: 
`-I./MCAL -I./HAL.`

#### Source Files

You must list the relative path to every single .c file that contains code you are actively using.

> If you have subdirectories (e.g., `MCAL/DIO/DIO.c`), you will need to specify those exact paths for both the `-I` flags and the `.c` files. This exact scaling problem is the primary reason developers eventually switch to Makefiles, as the terminal command becomes far too long to type repeatedly.


### Makefile

```Makefile
# Target microcontroller and clock frequency
MCU = atmega32
F_CPU = 16000000UL

# Programmer configuration
PROGRAMMER = usbasp
PORT = usb

# Compiler and tools
CC = avr-gcc
OBJCOPY = avr-objcopy
AVRDUDE = avrdude

# Compiler flags
CFLAGS = -Os -Wall -mmcu=$(MCU) -DF_CPU=$(F_CPU)

# Project name and source files
TARGET = main
SRCS = $(wildcard *.c)
OBJS = $(SRCS:.c=.o)

# Default build target
all: $(TARGET).hex

# Compile C files to object files
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

# Link object files into an ELF file
$(TARGET).elf: $(OBJS)
	$(CC) $(CFLAGS) $(OBJS) -o $@

# Generate the HEX file from the ELF file
$(TARGET).hex: $(TARGET).elf
	$(OBJCOPY) -O ihex -R .eeprom $< $@

# Flash the HEX file to the microcontroller
flash: $(TARGET).hex
	$(AVRDUDE) -c $(PROGRAMMER) -p $(MCU) -P $(PORT) -U flash:w:$<:i

# Remove compiled build files
clean:
	rm -f *.o *.elf *.hex

.PHONY: all flash clean
``` 

How to use this?
Open your terminal in the project folder and type make.
Because of the `$(wildcard *.c)` directive, it will automatically find, compile, and link every C file in the directory. You will know it succeeded when main.hex appears in your folder.

Plug in your kit and type make flash. This command automatically builds the code if there are new changes, converts it, and runs avrdude to upload it to the hardware.

If you need to clean:
Type make clean to delete all generated .o, .elf, and .hex files. This is useful for forcing a fresh build from scratch or cleaning up the directory before pushing your code to a repository.

#### Flags Meaning

##### `-Os` (Optimize for Size)

###### The Problem:

Microcontrollers like the ATmega32 have extremely limited storage (only 32 KB of flash memory). Normally, desktop compilers optimize for execution speed (`-O2` or `-O3`), which often bloats the final file size by unrolling loops or duplicating code.

###### The Solution:

`-Os` instructs avr-gcc to prioritize memory. It enables all speed optimizations that do not increase the binary size, while specifically applying algorithms designed to shrink the footprint of your machine code so it safely fits onto the chip.

##### `-Wall` (Warnings All)

###### The Problem: 

The C language allows you to write code that perfectly follows syntax rules but contains logical flaws that will cause catastrophic bugs on your hardware.

###### The Solution: 

`-Wall` tells the compiler to act as a strict proofreader. It will print warnings in your terminal if it spots common C pitfalls, such as declaring a variable but never using it, using a variable before it is initialized, or accidentally typing an assignment `if(x = 5)` instead of a comparison `if(x == 5)`.

### MakeFile For Folders

This updated version introduces an automated way to handle layered architectures without hardcoding every single C file or header path.

```Makefile
# Target microcontroller and clock frequency
MCU = atmega32
F_CPU = 16000000UL

# Programmer configuration
PROGRAMMER = usbasp
PORT = usb

# Compiler and tools
CC = avr-gcc
OBJCOPY = avr-objcopy
AVRDUDE = avrdude

# Directories containing source code and headers
# Add any other folders you create (e.g., APP, LIB) to this list separated by spaces
SRC_DIRS = . MCAL HAL

# Find all .c files in the specified directories
SRCS = $(foreach dir, $(SRC_DIRS), $(wildcard $(dir)/*.c))

# Generate the corresponding .o object file paths
OBJS = $(SRCS:.c=.o)

# Automatically generate the -I include flags for every directory
INC_FLAGS = $(foreach dir, $(SRC_DIRS), -I$(dir))

# Compiler flags
CFLAGS = -Os -Wall -mmcu=$(MCU) -DF_CPU=$(F_CPU) $(INC_FLAGS)

# Project name
TARGET = main

# Default build target
all: $(TARGET).hex

# Compile C files to object files
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

# Link object files into an ELF file
$(TARGET).elf: $(OBJS)
	$(CC) $(CFLAGS) $(OBJS) -o $@

# Generate the HEX file from the ELF file
$(TARGET).hex: $(TARGET).elf
	$(OBJCOPY) -O ihex -R .eeprom $< $@

# Flash the HEX file to the microcontroller
flash: $(TARGET).hex
	$(AVRDUDE) -c $(PROGRAMMER) -p $(MCU) -P $(PORT) -U flash:w:$<:i

# Remove all compiled build files, including those inside subfolders
clean:
	rm -f $(OBJS) $(TARGET).elf $(TARGET).hex

.PHONY: all flash clean
```

# Clock

A clock singal is a square signal that repeats itself every period of time called a cycle.

Every Cycle has levels, either Logical Low or Logical High.
The transition from **Low** to **High** is called ***Rising Edge*** and the transition from **High** to **Low** is called ***Falling Edge***.

If we have a cycle of $Time \space Period \space = \space 0.1ms$, then the $Frequency$ is the reciprocal of the $Time \space Period$ which is $\frac{1}{0.1} = 10 \space Cycles/second \space (Hz)$.

If the frequency increase this means that the cycle period decreases. Which means that the clock signal (rate) is fast.

## Clock Circuits

There is some circuits that can be used to generate this clock signal:
- RC Circuit Clock Generator.
- Crystall Oscillator Clock Generator.

### RC Clock Generator
It is a circuit of a *Resistor* and a *Capacitor* where the voltage oscialltes in between them.

![RC clock generator circuit showing a resistor and capacitor connected to produce an oscillating clock signal.](/Interfacing/Attachments/RC-Clock.png)

It is considered the cheapest option, but its tolerance is high which means it is really noisy (not precise) and it has bad accuracy.

Bad Accuracy occurs when you set it to give you as an example 16 Hz and it gives you 20 Hz instead.
(Frequency is false).

Bad Precision occurs when you set it to give you as an example 16 Hz and it gives you 16 Hz but it keeps tolerating around it.
(Frequency is not stable).

It also drifts by temperatue, and in some old MCUs, the tolerance of the RC Clock Generator can be around $-20\%$.

Normally it is found inside the internal MCU Architecture, to be able to operate your chip even if you have no external clock generators.

### Crystal Oscillator Clock Generator

Crystal Oscillators are much more precise and accurate.
They have wido range of frequency choice as crystals comes in wide range of frequencies.

![16 MHz crystal oscillator component used as a precise external clock source for a microcontroller.](/Interfacing/Attachments/16MHZ_Crystal.jpg)

Normally the crystal oscillator is associated with 2 capacitors in parallel to help smoothing the voltage.

They can be packaged together into a crystal resonator.

![Packaged crystal resonator used as a compact external clock source.](/Interfacing/Attachments/crystal-resonator.jpg)

## ATmega32 Clock Configuration
Our MCU has an internal RC Circuit Clock Generator that can generate frequencies of $1MHz$, $2MHz$, $4MHz$, and $8MHz$.

The Processor of ATmega32 can work on frequencies up to $16MHz$ where it can execute approximately number of instructions equals the rate the processor is working on.

If the processor is operating on $16MHz$ it can deliver $16 \space MIPS$ (Million Instructions Per Second).

If you are using an external clock generator like crystal oscillator or 555 Timer or others, you have to connect them on the *XTAL1* and *XTAL2* pins.
If you are using crystall oscillator you will use the 2 pins, while if you are using 555 Timer Clock Generator Circuit you will use only one of them and the other will be a normal *GPIO* pin.

There is some internal fuses inside the MCU, Low Fuses (8 Fuses) and High Fuses (8 Fuses).

They control some tasks of the controller, some of them if programmed, the MCU will behave like something, if not programmed, the MCU will behave something different.

Some of these fuses are by default programmed (Initially Low) and some others are by default unprogrammed (Initially High). We can find their initial state using the datasheet.

The Least Significant 4 Fuses in the Low Fuses + the fifth Fuse in the High Fuses are the ones responsible for clock configuration.

The Least Significant 4 Fuses in the Low Fuses are called:
- CKSEL0 (Programmed by Default)
- CKSEL1 (Unprogrammed by Default)
- CKSEL2 (Unprogrammed by Default)
- CKSEL3 (Unprogrammed by Default)

The fifth fuse in the High Fuses is called:
- CKOPT

![ATmega32 low fuse byte diagram identifying the fuse bits used for clock-source configuration, including CKSEL bits.](/Interfacing/Attachments/Fuse-Low-Byte-Table.png)

These bits allows us to configure the MCU on the internal clock according to the following table:

| CKSEL3 | CKSEL2 | CKSEL1 | CKSEL0 |                   |
|--------|--------|--------|--------|-------------------|
|   0    |   0    |   0    |   1    | Internal RC 1 MHZ |
|   0    |   0    |   1    |   0    | Internal RC 2 MHZ |
|   0    |   0    |   1    |   1    | Internal RC 4 MHZ |
|   0    |   1    |   0    |   0    | Internal RC 8 MHZ |

> Note: By default the Least Significant 4 fuses are like this `0b0001` which means that the default clock for the MCU is $1 MHz$.

> That's why inside the delay header you will find it defining the default value of `F_CPU` with `1000000UL` which is $1 MHz$. 

### External RC Clock Generator

If you want to configure the MCU to an external RC Clock Generator or 555 Timer Generator, first you need to connect it through the *XTAL1* pin and leave the *XTAL2* NC (Not Connected).

![External RC clock configuration for an ATmega32, with the clock source connected to XTAL1 and XTAL2 left unconnected.](/Interfacing/Attachments/External-RC-HW-Conf.png)

You can adjust the actual frequency of the clock generator using the values of the resistor and capacitor.

The datasheet defines the frequency by a simple equation:

$ Freq \space = \space \frac{1}{3 \times R \times C}$

The datasheet estimates the frequency by this equation, it is not accurate (as we talked earlier about the cons of RC Circuit).
But the capacitor value should be at least $22pF$.

![Datasheet excerpt describing the ATmega32 external RC oscillator configuration and its frequency range.](/Interfacing/Attachments/External-RC-Paragraph-Datasheet.png)

So, Let's say that you have a capacitor of value $22pF$ and you need to operate your MCU on $8 MHz$. Now to know the right resistor value to put in the circuit we only substitue in the rule:

$8 \space \times \space 10^{6} = \frac{1}{3 \space \times \space R \space \times \space 22 \space \times \space 10^{-12}}$

Which is:

$R = \frac{1}{3 \space \times \space 8 \space \times \space 10^{6} \space \times \space 22 \space \times \space 10^{-12}} \space \Omega$

If you program the *CKOPT* Fuse (fifth Fuse in High Fuses) This will enable the internal capacitor of the MCU, so you don't need the external capacitor.

The inernal capacitor of the MCU has a nominal value of $36pF$.

To configure external RC Clock Generator in the MCU, you need to tweak the *CKSEL* Fuses like this:


| CKSEL3 | CKSEL2 | CKSEL1 | CKSEL0 |                            |
|--------|--------|--------|--------|----------------------------|
|   0    |   1    |   0    |   1    | External RC 0.1 - 0.9 MHZ  |
|   0    |   1    |   1    |   0    | External RC 0.9 - 3.0 MHZ  |
|   0    |   1    |   1    |   1    | External RC 3.0 - 8.0 MHZ  |
|   1    |   0    |   0    |   0    | External RC 8.0 - 12.0 MHZ |

> Normally we don't connect the ATmega32 to its maximum clock rate (16 MHz) as the controller faces some problems syncronizing this high speed clock.

### External Crystall Oscillator Clock Generator

![Datasheet excerpt showing the ATmega32 crystal or ceramic resonator oscillator circuit with two load capacitors.](/Interfacing/Attachments/Crystall-Osc-Datasheet.png)

Those capacitors can be from $12pF$ to $22pF$.

To configure external crystal oscillator in the MCU, you need to tweak the *CKSEL* Fuses and the *CKOPT* Fuse like this:

| CKOPT | CKSEL3 | CKSEL2 | CKSEL1 | CKSEL0 |                         |
|-------|--------|--------|--------|--------|-------------------------|
|   1   |   1    |   0    |   1    |   x    | Resonator 0.4 - 0.9 MHZ |
|   1   |   1    |   1    |   0    |   x    |  Crystal 0.9 - 3.0 MHZ  |
|   1   |   1    |   1    |   1    |   x    |  Crystal 3.0 - 8.0 MHZ  |
|   0   |   x    |   x    |   x    |   x    |   Crystal 1.0 <= MHZ    |

> The first option can not be used with crystals, only with resonators.

If you need to connect any external sources like TTL or IC 555 set the *CKSEL* into *0000*.

# Low Fuses Byte
As we talked above about the Low Fuse Byte, we discovered the least significant 4 bits of this byte.

![ATmega32 low fuse byte diagram identifying the fuse bits used for clock-source configuration, including CKSEL bits.](/Interfacing/Attachments/Fuse-Low-Byte-Table.png)

## SUT Bits
`SUT0` and `SUT1` are responsible for something called the *start-up time*.
*Start-up time* is the time the controller takes starting from connecting it with power till it starts executing program. This time is configured through these bits, but normally we do not need to change them, we leave them to default.

## Brown-out Bits
`BODEN` and `BODLEVEL` are responsible for Brown-Out Detetion. The default value for `BODEN` is unprogrammed - 1 -which means that the Brown-Out Detection Enable is disabled, if you want to enable it you need to program the `BODEN` Fuse (Make it 0). Brown-Out Detection is a circuit inside the MCU, to be able to understand what it does we need to take a step back.

Do you remember when we talked in the early 2 sessions about the relation between the voltage applied to on the $V_{CC}$ and the Clock Rate applied to the MCU?

If you applied very low voltage you will be restricted to a specific range of Clock rates.

If you do otherwise you'll find your MCU out of sync and behaves unexpectedly, so you need a circuit that keeps an eye on the $V_{CC}$ Voltage, if it drops it alerts you.

The Brown-Out Circuit does this, it keeps an eye on the $V_{CC}$ Voltage and if it drops or something happens to it, it resets the MCU, and if the problem continues it keeps reseting it, preventing it from executing anything as if it continued execution it will behave wrong.

The `BODLEVEL` determines the level where the Brown-Out Detection circuit will reset at, if it is unprogrammed (1) it will reset below $2.7V$, but if it's programmed (0) it will reset below $4V$.

So, if we enable the circuit by the `BODEN` the circuit will compare the $V_{CC}$ voltage level with the value set by `BODLEVEL`.

The default values for these fuses is disabled and $2.7V$.

### The sequence is as follows:

There is 2 levels around the `BODLEVEL`, if the `BODLEVEL` is set to $2.7V$, you will find the Brown-Out Detection Circuit has 2 levels around it called $V_{BOT^{+}}$ and $V_{BOT^{-}}$.

If `BODLEVEL` is $2.7V$ you will find $V_{BOT^{+}} \space = \space 2.9V$ and $V_{BOT^{-}} \space = \space 2.9V$.

If `BODLEVEL` is $4V$ you will find $V_{BOT^{+}} \space = \space 4.2V$ and $V_{BOT^{-}} \space = \space 3.6V$.

If the $V_{CC}$ dropped below the $V_{BOT^{-}}$ the MCU faces internal reset and keeps reseting till the $V_{CC}$ raises again higher than $V_{BOT^{+}}$.

If the $V_{CC}$ has managed to raise higher than $V_{BOT^{+}}$, then a time-out circuit is enabled that counts a period of time to wait and see if the $V_{CC}$ has managed to stay higher than the $V_{BOT^{+}}$, if so it cancels the reseting.

![placeholder](/Interfacing/Attachments/Brown-Out-Detection-During-Operation.png)

There is something called $t_{BOD}$ which stands for the *Time of Brown-Out Detection Circuit*.
If the $t_{BOD}$ is $0.2us$ this means that if the $V_{CC}$ dropped below the $V_{BOT^{-}}$ for $0.1us$ the reset will not activate. It needs to drop below the $V_{BOT^{-}}$ for a time greatere than the $t_{BOD}$ to activate the reset. 

This technique protects from the flactuations that happens to $V_{CC}$.

# High Fuses Byte

We have talked earlier about the fifth bit (Fuse 4) that is named *CKOPT*.
Now let's view the rest of it.

### *SPIEN*
It's responisble for enabling the *SPI programmer*.
The default of this bit is programmed (0) (Enabled), if you unprogram it, the external programmers won't work. You won't be able to upload your code using usbasp.

> Take care if you unprogrammed it, you won't be able to use usbasp again or any serial programmer, which means you can not program it again. There is some ways to program it again, but in most cases if you unprogram it then you MCU is useless, you can not upload any code again to it.  

## *EESAVE*
It's responsible for the EEPROM Save. It is the fourth fuse (bit 3). It can control wether the data on the EEPROM will be deleted when you delete the data on the flash or not.
Erasing the flash can be done in two ways, one of them is overwriting it with new code, the other is via avrdude.

## *OCDEN* and *JTAGEN*

### What is External Debugger?
*PC2*, *PC3*, *PC4*, and *PC5* pins have an alternate function other than being an GPIO pins they can be used to be external debugger pins.

The external debugger communicates with the MCU using a *JTAG* protocol. The debugger can access the MCU registers and memories and debug everything and view everything inside it.

*JTAGEN* is responsible for external debugger. The *JTAGEN* is responsible for enabling the JTAG protocol, It is programmed (0) (enabled) by default.

Since it is enabled by default, sometimes the Pins *PC2*, *PC3*, *PC4*, and *PC5* doesn't work correctly, so you need to disable it if you are not using the debugger.

*OCDEN* is responsible for enabling the On-Circuit Debugger. This fuse is by default unprogrammed (1) (disabled) which means that the debugger can not access the internal registers or memories of the MCU.

## *BOOTRST*, *BOOTSZ0*, and *BOOTSZ1*

### What is Bootloader?
Bootloader is an optional code by default is not written, if it is written, it is written in flash memory.
Flash's segments like `.data`, `.rodata`, `.text` and `IVT` are called Application Sector, Flash has another sector called bootloader.

> Remember that `.text` segment has a part called start-up code, and in the end of the start-up code it calls the main.
> In some MCUs the start-up code is a part of the `.text` or may be a separated segment.
> The start-up code is the first thing that runs on your MCU when it connects to power.

You can make the bootloader code runs before the start-up code using the *BOOTRST* fuse.
The *BOOTRST* is by default unprogrammed (1) (disabled) which means it first executes the application reset (Reset vector = Application reset) (address $0000) which is the start-up code,
if you program it (0) (enable) it will execute the bootloader code first (Reset vector = Boot Loader Reset).

You can put a code in the Boot Loader that can be used to tell the MCU that you can upload program code (update the `.text` segment) without using *SPI* or External Programmer,so you can update the `.text` segment using UART or USB to TTL chip like the Arduino, you can use anything you can even update your code wireless.

Even the external programmer like usbasp has an internal MCU (ATmega8) that contains the boot loader's logic.

### Memory Layout
We know that at ATmega32 the flash memory size is 32Kbytes where every location (word) has 2 bytes (16 bits) so you have 16 Klocation which is $2^{14}$ word.

The memory itself using byte addressing is $2^{15}$ bytes which is $2^{14}$ words, as each word is $2$ bytes.

As we talked earlier in the first two sessions about the processor-flash interfacing we mentioned that the processor interfaces with the flash memory with 16 data lines, which makes the word size is 2 bytes and the IR is 1 word length.

So the PC is 14 bits long, and the address lines are 14 bits long to be able to interface with the $2^{14}$ words.

The assembly instructions in AVR some of them are 16 bits long and some others are 32 bits.

#### `LDI`
This 2-byte assembly instruction is called load immediate, it loads a number to 16 registers of the 32 general purpose registers (R16 - R31).

It's typed like this: `LDI Rd K`

`1110 KKKK dddd KKKK`

Of this 16 bits, the first 4 bits is for opcode, the second and the fourth 4 bits are used for the value of k, from 0 to 255, the third 4 bits presents the value of d of the Rd where d is set between 16 to 31.

if `dddd` is `0000` this means `R16`,
if it is `1111` this means `R31`.

#### `ADD`

This 2-byte assembly instruction is called Addition, it adds two general purpose registers (R0 - R31).

It's typed like this: `ADD Rd Rr`

`0000 11rd dddd rrrr`


Of this 16 bits, the first 6 bits is for opcode, then the $7^{th}$ bit and the last four bits are used for the value of the r of Rr where r is set between 0 and 31, and the five bits from the $8^{th}$ to the $12^{th}$ bit are used for the value of the d of Rd where d is set between 0 and 31.

---

*BOOTSZ0* and *BOOTSZ1* are responsible for setting the size of the boot loader in words.

![placeholder](/Interfacing/Attachments/Boot-Loader-Size-Conf.png)

As you can see if you set them to `11`, you will find the boot loader's size is 256 words, and the rest of the flash memory - $2^{14}$ words - is for the application part (`.text`, IVT, ...).

# Clock Summary

## Overview — CKSEL3..0 selects the clock source family

| CKSEL3..0 | Clock Source |
|---|---|
| 0000 | External Clock |
| 0001 – 0100 | Calibrated Internal RC Oscillator |
| 0101 – 1000 | External RC Oscillator |
| 1001 | External Low-Frequency Crystal (32.768 kHz) |
| 1010 – 1111 | External Crystal / Ceramic Resonator |

**Default from factory:** CKSEL = 0001, SUT = 10 → 1 MHz internal RC oscillator with the longest startup time.

(Note: "1" = fuse unprogrammed, "0" = fuse programmed.)

## 1. Calibrated Internal RC Oscillator (CKSEL3..0 = 0001–0100)

| CKSEL3..0 | Frequency |
|---|---|
| 0001 | 1 MHz |
| 0010 | 2 MHz |
| 0011 | 4 MHz |
| 0100 | 8 MHz |

CKOPT should stay unprogrammed (1) with this option.

## 2. External RC Oscillator (CKSEL3..0 = 0101–1000)

| CKSEL3..0 | Frequency range |
|---|---|
| 0101 | ≤ 0.9 MHz |
| 0110 | 0.9 – 3.0 MHz |
| 0111 | 3.0 – 8.0 MHz |
| 1000 | 8.0 – 12.0 MHz |

Programming CKOPT here enables an internal ~36 pF capacitor between XTAL1 and GND, removing the need for an external one.

## 3. External Low-Frequency Crystal (CKSEL3..0 = 1001)

Used for a 32.768 kHz watch crystal. Programming CKOPT enables internal 36 pF capacitors on XTAL1/XTAL2.

## 4. Crystal / Ceramic Resonator (CKSEL3..0 = 1010–1111) — this is where CKOPT actually changes behavior

Here CKSEL3..1 (three bits) picks the frequency band, CKSEL0 + SUT1..0 pick startup timing, and **CKOPT selects the oscillator's amplifier mode**:

| CKOPT | CKSEL3..1 | Frequency range | Recommended C1/C2 |
|---|---|---|---|
| 1 (unprogrammed) | 101 | 0.4 – 0.9 MHz | — (resonators only, not crystals) |
| 1 (unprogrammed) | 110 | 0.9 – 3.0 MHz | 12–22 pF |
| 1 (unprogrammed) | 111 | 3.0 – 8.0 MHz | 12–22 pF |
| 0 (programmed) | 101, 110, or 111 | ≥ 1.0 MHz (up to the part's max) | 12–22 pF |

So effectively:
- **CKOPT = 1 (unprogrammed):** smaller output swing, lower power, limited to the ranges above, cannot drive another clock buffer.
- **CKOPT = 0 (programmed):** full rail-to-rail swing, wide frequency range, needed for noisy environments or to drive a second device's clock input. For resonators, this raises the max usable frequency from 8 MHz (CKOPT=1) to 16 MHz (CKOPT=0). A common example: for a 16 MHz crystal, use CKSEL3..0 = 1111 with CKOPT programmed (0).

## 5. External Clock (CKSEL3..0 = 0000)

No CKOPT dependency - the device just takes a clock signal directly on XTAL1.

# How to Control Fuses using Toolchain
To control the internal fuse bits, you use the exact same `-U` memory operation flag in `avrdude` that you use to flash your `.hex` application code. Instead of targeting the `flash` memory, you target the `lfuse` (Low Fuse) or `hfuse` (High Fuse) memory spaces.

Here is the standard command structure using your `usbasp` programmer and `atmega32` controller:

```bash
avrdude -c usbasp -p m32 -U lfuse:w:0xFF:m -U hfuse:w:0x99:m
```

### Parameter Breakdown

* `lfuse` / `hfuse**`: Specifies which fuse byte you want to interact with.
* `w`: Instructs `avrdude` to perform a write operation.
* `0xFF`: The hexadecimal value you want to write. (Remember that fuses are active-low: `0` is programmed, `1` is unprogrammed).
* `m`: Tells `avrdude` that the value provided is an immediate value written directly in the command line, rather than a file path.

---

## Safe Fuse Flashing Procedure

Because writing the wrong clock configuration (like setting it to an external clock when you don't have one connected) can lock you out of the microcontroller, it is critical to follow a safe sequence.

1. **Read current fuse values:** Verify communication and baseline configuration.
Run a read command to see the current state before changing anything. This ensures your programmer is communicating properly and gives you a fallback value.

```bash
avrdude -c usbasp -p m32 -U lfuse:r:-:h -U hfuse:r:-:h
```

The `-` tells `avrdude` to output the result directly to the terminal instead of saving a file, and `h` formats the output as hexadecimal.


2. **Calculate the new hexadecimal value:**
Convert your desired bitmask into a hex value. For example, if you want an external 16 MHz crystal with the longest startup time (CKSEL=1111, SUT=11) and default Brown-out (BODEN=1, BODLEVEL=1), your Low Fuse binary is `1111 1111`. In hexadecimal, this is `0xFF`.


3. **Write the new fuses:**
Execute the write command using the immediate `m` flag.

```bash
avrdude -c usbasp -p m32 -U lfuse:w:0xFF:m
```

`avrdude` will write the value and immediately read it back. Do not disconnect the programmer until the terminal confirms the verification was successful.

## Integrating Fuses into your Makefile

Typing immediate hex values into the terminal can be risky. Since you are already utilizing a Makefile for your layered architecture, you can automate this by adding a dedicated `fuses` target.

Add the fuse values as variables at the top of your Makefile:

```makefile
# Fuse configurations (Example: 16MHz External Crystal, JTAG disabled)
LFUSE = 0xFF
HFUSE = 0xC9
```

Then, add a new build target alongside your `flash` and `clean` commands:

```makefile
# Burn fuses to the microcontroller
fuses:
	$(AVRDUDE) -c $(PROGRAMMER) -p $(MCU) -P $(PORT) -U lfuse:w:$(LFUSE):m -U hfuse:w:$(HFUSE):m

```

Now, whenever you move to a fresh ATmega32 chip, you can simply open your Linux terminal and run `make fuses` once to configure the clock and debugging settings, followed by `make flash` to upload your application.
